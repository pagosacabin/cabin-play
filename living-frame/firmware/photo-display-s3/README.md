# photo-display-s3 — LCD_CAM VGA scanout proof on the ESP32-S3 (task 0179, rung 3a)

A 640×480@60 VGA signal generated by the **ESP32-S3 LCD_CAM peripheral** (via
`esp_lcd`'s RGB-panel driver), carrying a **320×240** one-byte-per-pixel frame
that is **pixel-doubled 2×2 inside the DMA bounce-buffer ISR**.

Target: the bench **Heltec WiFi LoRa 32 V3 — ESP32-S3FN8, 8 MB flash, no PSRAM**,
identified on the wire as MAC `9c:13:9e:a1:37:40` on `/dev/ttyUSB1`.

This rung proves the *driver*, not a look. The 0178 gate established that FabGL
cannot drive VGA on the S3 (its VGA is the classic ESP32's I2S LCD mode) and
that this board has no PSRAM, so 640×480×1 B = 307,200 B cannot be held in RAM.
Rung 3a answers the next question: can the S3's own RGB peripheral produce a
real 640×480 signal from a frame buffer that *does* fit?

## Why this shape

`esp_lcd`'s RGB driver can run in `no_fb` mode: it allocates no screen-sized
frame buffer and instead calls `on_bounce_empty` for every 10,240-byte chunk it
needs. That is the whole design:

```
 320×240 buffer (76,800 B, internal RAM, address printed at boot)
        │  scanout_double_fill(): x doubled by byte expansion,
        │                        y doubled by reading source line (line >> 1)
        ▼
 2 × 10,240 B bounce buffers in DRAM  ──►  LCD_CAM RGB, 8-bit bus, 25 MHz pclk
                                                 │
                                       R2G2B2 ladder + HSYNC 38 + VSYNC 39 ──► 213T
```

307,200 / 10,240 = **30 bounce fills per frame**, which is exactly what the
device's own counters report at runtime (`+30.0/frame` in the console capture).

The shape — byte-per-pixel, `data_gpio[8]` with unused lines at `-1`, small
internal-RAM bounce buffers, 640×480@60 — follows **PicoMite's
`drivers/vga_lcdcam_s3/vga_lcdcam_s3.{c,h}`**, the precedent the 0178 gate
evidenced (its README: *"The peripheral owns a single PSRAM frame buffer of
HRes*VRes bytes (one RGB332 byte per pixel), then feeds LCD DMA through small
internal-RAM bounce buffers"*). **What this rung changes:** PicoMite needs PSRAM
for a full 640×480 RGB332 frame; this board has none, so the frame buffer is
320×240 and the DMA feed does the doubling. Everything else (per-line GPIO map
with `-1` for unused lines, bounce buffers, byte-per-pixel encoding) is the same.

## Pin map → data byte, with no translation

Agreed map (fixed by the task; Stephen has wired to this):

| Signal | GPIO | frame-byte bit | notes |
|---|---|---|---|
| R MSB  | 4  | bit 1 | 270 Ω path |
| R LSB  | 5  | bit 0 | 470 Ω path |
| G MSB  | 6  | bit 3 | |
| G LSB  | 7  | bit 2 | |
| B MSB  | 19 | bit 5 | |
| B LSB  | 20 | bit 4 | |
| HSYNC  | 38 | — | active low (VGA negative polarity) |
| VSYNC  | 39 | — | active low |

The buffer byte is packed `(B<<4)|(G<<2)|R` with each 2-bit field `(MSB,LSB)` —
the same packing rung 2 used — so **bit *n* of a buffer byte goes to
`data_gpio_nums[n]`** and the byte reaches the ladder untouched:

```
data_gpio_nums[0..7] = { 5, 4, 7, 6, 20, 19, -1, -1 }
```

`pclk` and `de` are deliberately routed to **no pin** (`-1`): a VGA DE-15
connector carries R/G/B + HSYNC + VSYNC only, so a 25 MHz pin would be pure EMI.
The monitor rebuilds pixel timing from HSYNC.

## Timing

640×480@60 VESA: 800 × 525 total, pclk requested 25.000 MHz from the 160 MHz PLL
(divide by 6.4), giving 59.52 Hz nominal. The device measured **59.40–59.77 Hz**
over 75 s of VSYNC interrupts, i.e. an effective pixel clock of
59.56 × 800 × 525 ≈ **25.02 MHz**.

## Image pipeline: pre-converted on the host, not decoded on device

Choice (task step 4 allows either): **pre-convert and embed byte arrays**.

- `tools/convert_images.py` decodes the two 640×480 JPEGs, 2×2 box-averages to
  320×240 (the same reduction TJpgDec's 1/2 descale performs), quantises to the
  **measured** ladder levels — 0 / 0.452 / 0.714 / 1.000, *not* 0/85/170/255 —
  and dithers in **linear light** (0177 round-2 finding: voltage-domain dither
  made shadows speckle). Output: `src/images.h`, 76,800 B per image (~784 K of
  source text), embedded in flash and `memcpy`'d into the internal-RAM frame at
  each phase switch.
- Palette entries actually used: lorikeet 46 of 64, Blue Marble 24 of 64.
- Rung 2's on-device TJpgDec path was not reused: with no PSRAM, a decoder work
  pool + stream buffer on top of the 76,800 B frame is avoidable cost for two
  fixed images.

## Content cycle

`ramp 30 s → lorikeet 20 s → Blue Marble 20 s`, repeating (task step 3). The ramp
screen is rung 2's, re-used verbatim: `src/ramp_screen.h` is a copy of
`photo-display-64/src/ramp_screen.h` with **one** edit (its include of
`photo_render64.h` became `ladder64.h`, the ladder/quantiser extracted from it
with no value changed), so a photograph of this rung's ramp means the same thing
as rung 2's. `src/ladder64.h` keeps the old `photo64*` names as macros so the
copied drawing code stays untouched.

## Build, flash, capture

```bash
pio run -e heltec-s3                 # ESP-IDF 5.5 via PlatformIO
pio run -e heltec-s3 -t upload       # upload_port = /dev/ttyUSB1 (CP2102)
/usr/bin/python3 bench/capture.py /dev/ttyUSB1 80 > bench/console.txt
```

`upload_port` is pinned to `/dev/ttyUSB1` on purpose: the bench also has an
ESP32-C3 on `/dev/ttyACM0` and a classic ESP32-D0WD on `/dev/ttyUSB0`
(`bench/identity.log` records the target's `read_mac`).

Trap worth knowing: PlatformIO generates `sdkconfig.heltec-s3` from
`sdkconfig.defaults` and then **reuses** it, silently ignoring later edits to the
defaults. It is gitignored here, so a fresh clone regenerates it; it was deleted
and rebuilt once to confirm the committed defaults alone produce the same image
size (382,839 B) and the same runtime behaviour.

## What is proven, and what is not

**Proven here:** it builds and flashes; the RGB peripheral accepts the 8-bit
6-line GPIO map, the `no_fb` + bounce-buffer configuration and the 640×480
timing, and runs without a driver error; the scanout is free-running at
59.4–59.8 Hz with exactly 30 bounce fills per frame for 75 s across all three
phases (a DMA that starved or a desynced restart path would show as a wrong
ratio); the pixel content and the doubling are verified on the host byte for
byte, including the shipped ISR code.

**Not proven here:** that the 213T locks, that the syncs leave the board at TTL
levels the monitor accepts, or that the ladder levels look right on the panel.
No instrument on this host can see the VGA cable. That is the acceptance gate —
**Stephen's photographs plus his word** — and nothing in this directory should be
read as a substitute.

### One defect this process caught

The first build shipped `w = a * 0x00010001u` in the pair-expansion fast path,
which puts the duplicate in the *upper half* of the word: every second output
byte came out `0x00`, i.e. a black column between every source pixel. The console
was clean and the scanout counters were perfect — only `tools/scanout_test.cpp`
(byte-comparing the ISR's output against a 2×2 nearest-neighbour reference with
live negative controls) showed it. Fixed to `0x0101`, re-flashed, and the fix is
what is on the board now.
